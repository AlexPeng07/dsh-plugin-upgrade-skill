### DSH-0.2.0-RC1-01 · Host packages cross to 0.2.0-rc.1; every `^0.1.x`-floored DSH peer is refused, and `^0.2.0` does not admit `0.2.0-rc.1`

- **Type**: breaking
- **Applies to**: every plugin whose `peerDependencies` declares `@deepseek-ai/dsh` or `@deepseek-ai/dsh-*` (the enforcement mechanism itself shipped in 0.1.7-rc.1 — [DSH-0.1.7-RC1-01](v0.1.7-rc.1.md); what is new here is the version boundary)
- **Touchpoints**: none (packaging/dependencies special surface — pre-flight §0 `peerDependencies` inventory)
- **Action level**: required-if-hit
- **Symptoms**:
  - Upgrading the host from any 0.1.x to `0.2.0-rc.1` disables every installed plugin whose DSH peer floor is `^0.1.x`: stderr shows `dsh: disabling profile plugin row "<id>": Plugin … is incompatible with dsh 0.2.0-rc.1: peerDependencies {...}`. The profile files are unchanged; the row silently stops mounting.
  - **The naive fix is refused too.** `^0.2.0` expands (semver ≥ 7.8.3, `includePrerelease: true`) to `>=0.2.0 <0.3.0-0`, and `0.2.0-rc.1 < 0.2.0` — so the rc host itself does not satisfy it. Measured against `0.2.0-rc.1` with the shipped `semver`:

    | Result | Ranges |
    |---|---|
    | Refused | `^0.1.0`, `^0.2.0`, `^0.1.0 \|\| ^0.2.0` |
    | Admitted | `^0.2.0-rc.1`, `>=0.1.0 <0.3.0`, `>=0.1.0 <0.3.0-0`, `*`, `workspace:*` / `workspace:^" (treated as the running version) |

    `^0.2.0-rc.1` also admits the future `0.2.0` final and 0.2.x patches, so it is the recommended floor form for the whole 0.2 window.
- **Migration recipe**:
  1. Rewrite each DSH peer as `^0.1.0 || ^0.2.0-rc.1` (keeps 0.1.x hosts installable) or `^0.2.0-rc.1` (0.2-only).
  2. Ship the peer fix as a plugin release; the host re-reads the installed `package.json` on the next boot — no exemption needed.
  3. If you must run a mismatching build now, `dsh plugin allow-version <name>@<version> --dsh-version 0.2.0-rc.1 --accept-risk` (profile-scoped, exact-version; see [DSH-0.1.7-RC1-01](v0.1.7-rc.1.md#dsh-017-rc1-01--dsh-peer-ranges-are-enforced-at-install-and-at-startup-017-does-not-admit-017-rc1) for the full grant mechanics).
- **Verification**: restart the host and assert stderr has no `disabling profile plugin row` line for your ids; `--dump-config` cannot detect a denial (see the rc.1 card's Verification section).
- **Source**: all `packages/*/package.json` version bumps at `dsh-v0.2.0-rc.1`; checker unchanged from rc.1 ([`packages/boot/app-boot/src/plugin-compatibility.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.1/packages/boot/app-boot/src/plugin-compatibility.ts)).
- **Field note** (first-hand, 2026-09-28): `@dsh-external/dsh-vision` (registers `view_image`) was disabled twice on the upgrade path — v0.1.0 with `^0.1.0`, then v0.1.1 with `^0.2.0` — and mounts again after shipping v0.1.1 with `^0.1.0 || ^0.2.0-rc.1`. The other six fleet plugins carry no DSH peers and were never refused.

### DSH-0.2.0-RC1-02 · Web work-details default moves to `detailed`; the saved `transcriptView` setting becomes optional

- **Type**: behavior
- **Applies to**: plugins that read the Chat settings schema (`transcriptView`) or assume the `standard` default; browser surfaces rendering transcripts
- **Touchpoints**: #2 (chat settings schema) if your plugin mirrors the field
- **Action level**: optional
- **Symptoms**: fresh Web clients (non-Desktop) now render `detailed` work details; the schema field becomes optional (`transcriptView?`, absence defers to the client default instead of coercing to `standard`); legacy saved values (`normal`, expanded) map to `detailed` instead of `standard`.
- **Migration recipe**: plugins that hard-code a `standard` fallback should read the schema default instead; plugins that persist the field may now omit it.
- **Verification**: fresh profile + fresh browser: transcript renders `detailed` without a saved setting.
- **Source**: [47db27a73](https://github.com/deepseek-ai/deepseek-harness/commit/47db27a73) `fix(ui-chat): resolve work-details defaults in client code`, [b066690f7](https://github.com/deepseek-ai/deepseek-harness/commit/b066690f7) `fix(web): default fresh work details to detailed`, [a03e63d1e](https://github.com/deepseek-ai/deepseek-harness/commit/a03e63d1e) `fix(ui-chat): map legacy normal work details to detailed`.

### DSH-0.2.0-RC1-03 · Schedule/time-context/ui-schedule rows leave the default web-app bundle; they ship as an optional bundle

- **Type**: breaking
- **Applies to**: plugins and user patches that insert rows before/after the `schedule`, `time-context`, or `ui-schedule` ids, or that assumed those services exist in a default web profile
- **Touchpoints**: #7 (profile patch composition)
- **Action level**: required-if-hit
- **Symptoms**: the three rows (previously shipped `disabled: true`) are removed from `packages/bundle/web-app/cordis.patch.yml` entirely; a new optional bundle ships them. A user patch or plugin that targeted them by id now has no such row to override, and code calling the Schedule service fails on default profiles.
- **Migration recipe**: install the optional schedule bundle where the feature is wanted, or drop the dependency. Bundle authors: re-run your row-id inventory against the new patch files before inserting.
- **Verification**: `dsh --profile web --dump-config` contains no `schedule`/`time-context`/`ui-schedule` rows on a default profile.
- **Source**: [41c29fa83](https://github.com/deepseek-ai/deepseek-harness/commit/41c29fa83) `feat(schedule): ship the Schedule switch as an optional bundle` and the schedule-bundle commit series; [`packages/bundle/web-app/cordis.patch.yml`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.1/packages/bundle/web-app/cordis.patch.yml).

### DSH-0.2.0-RC1-04 · Bundle composition gains telemetry rows: `otel` (base) and desktop-gated product analytics (web-app)

- **Type**: capability
- **Applies to**: bundles and plugins that insert into the same composition, plugin-manager duplicate-id diagnostics
- **Touchpoints**: #7
- **Action level**: informational
- **Symptoms**: `dsh-base` gains an `otel` row; `dsh-web-app` gains `desktop-product-telemetry` and `product-analytics` rows, both `disabled: !!js` unless the profile is `desktop`. A plugin or user patch inserting an id `otel` / `product-analytics` now collides with a bundle row (`duplicate loader entry id` boot failure).
- **Migration recipe**: rename colliding ids; if you mirror the rows, gate them the same way.
- **Verification**: boot once; a duplicate-id failure names the colliding id.
- **Source**: [b1cf871b2](https://github.com/deepseek-ai/deepseek-harness/commit/b1cf871b2) `feat(desktop): collect product analytics through OTel`; [`packages/bundle/base/cordis.patch.yml`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.1/packages/bundle/base/cordis.patch.yml).

### DSH-0.2.0-RC1-05 · `ISessions.fork` gains an optional `onCreated` callback; config-editor treats an own `config:` key as an override even when its value is undefined

- **Type**: capability
- **Applies to**: client plugins that fork sessions and want to observe the child before the optional rename; bundles whose patches set `config:` keys with undefined values
- **Touchpoints**: #4 (Remote/client contract), #7
- **Action level**: informational
- **Symptoms**: `fork(opts)` accepts `onCreated?: (childId: SessionId) => void` (existing calls unaffected). The settings/config projection now lets a profile patch's own `config:` key replace an inherited config even when the value is `undefined` — a previously invisible override now wins.
- **Migration recipe**: none required for existing calls; pass `onCreated` where the pre-rename child id is needed. Audit bundle patches that set `config:` keys to `undefined` — they now win over inherited values.
- **Verification**: fork and assert the callback fires before rename; set `config: { key: undefined }` in a patch and read the composed value.
- **Source**: [`packages/api/session-controller/src/client/contract/sessions.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.1/packages/api/session-controller/src/client/contract/sessions.ts), [`packages/boot/config-editor/src/index.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.1/packages/boot/config-editor/src/index.ts) at `dsh-v0.2.0-rc.1`.

### DSH-0.2.0-RC1-06 · Explorer path-opening spawns visible; the native-command runner gains a visibility argument — retire local reveal hotfixes

- **Type**: fix
- **Applies to**: fleet installs carrying local patches to `@deepseek-ai/dsh-native-command` that passed raw paths or forced `windowsHide: false` so reveal/open shows a window
- **Touchpoints**: #9 (subprocess behavior) if your plugin opens paths natively
- **Action level**: optional
- **Symptoms**: `runExplorer` now passes `'visible'` and `openInBrowser` passes `'hidden'` as a new runner argument; `explorerTarget` keeps the comma/equals encoding introduced in 0.1.7-rc.2. A local patch that rewrites `explorerTarget` to return raw paths now conflicts with the visible-window fix and can double-apply.
- **Migration recipe**: delete local reveal patches; the upstream form covers both the raw-path and window-visibility symptoms. Verify with a real `reveal` on Windows: an Explorer window opens with the file selected.
- **Verification**: reveal a file via the host tool; assert a visible Explorer window and no lingering headless `explorer.exe` process.
- **Source**: [a89506644](https://github.com/deepseek-ai/deepseek-harness/commit/a89506644) `fix(windows): keep Explorer path-opening windows visible` ([#5223](https://github.com/deepseek-ai/deepseek-harness/pull/5223)); [`packages/util/native-command/src/path-opener.ts`](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.0-rc.1/packages/util/native-command/src/path-opener.ts) at `dsh-v0.2.0-rc.1`.
- **Field note** (first-hand, 2026-09-28): the local fleet hotfix (raw-path + `windowsHide: false`, carried since 0.1.7-alpha.2) was retired on this upgrade; the upstream form was verified by code inspection and the rc.2 empirical reveal test.
